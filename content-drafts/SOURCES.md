### 1.2 年龄分布方式：事件本身没有年龄字段，靠「年龄池表」

这是与我们现行做法（每条事件写 min/max 年龄）最大的结构差异：

- `age.json` 为**每一个年龄单独列一张候选池表**：`{"年龄": {"age": n, "event": [条目...]}}`。
- 条目 = 事件 ID，可带权重后缀 `"事件ID*权重"`，无后缀默认权重 1。权重跨度极大：稀有事件 0.01–0.1、高频日常 2–10、人生里程碑（入学等）100–9999（近乎必触发）、被条件锁住的终局内容用天文数字权重（实际靠条件过滤，权重只是占位）。
- 池规模随年龄变化明显：0 岁池仅 6 条；2 岁约 43 条；4 岁约 110 条；7–11 岁约 190 条/岁（童年内容最密）；相邻年龄的池**高度重叠**（同一事件在连续多年池中反复出现，靠条件与「已发生」过滤实现一生一次）。
- 条件表达式里也能直接引用年龄（见 1.3 的 AGE 判断），等于有第二道年龄闸门。
- 对我们的启示：22–65 岁共 44 个年龄，若每岁维持 60–120 条候选池、事件平均跨 6–10 个年龄出现，则 500–800 条事件即可撑满；「年龄池 + 权重」比「min/max 区间」更容易调密度与稀有度。

### 1.3 事件本体字段（经典版 events.json）

一条事件 = 一个对象，字段如下（remake 版 `event.types.ts` 与经典版字段一致）：

| 字段 | 含义 |
|---|---|
| `id` | 数字 ID。段位粗分：1xxxx 为主线人生事件，2xxxx 多为天赋/特殊判定的分支目标，4xxxx 为修仙等终局线 |
| `event` | 事件正文（一句话为主） |
| `grade` | 稀有度 0–3，缺省 0；样本中绝大多数为 0，少数 1，极少 2 |
| `postEvent` | 可选：结果补述句（事件发生后追加的一句后果） |
| `effect` | 属性增量，键为 CHR 颜值 / INT 智力 / STR 体质 / MNY 家境 / SPR 快乐 / LIF 寿命 / AGE 年龄 |
| `NoRandom` | 为真则永不被随机抽到，只能由 branch 链条带入 |
| `include` | 条件表达式：**满足时才有资格被随机到**（前置条件） |
| `exclude` | 条件表达式：**满足时永不被随机到**（互斥/防重复） |
| `branch` | 数组，每项 `"条件:目标事件ID"`：本事件发生后按顺序判定条件，命中即跳转到目标事件（链式后续） |

### 1.4 条件系统：一个统一的小型表达式 DSL

所有条件（include / exclude / branch / 天赋触发）共用同一套语法：

- **运算对象**：五维属性（CHR/INT/STR/MNY/SPR）、年龄 AGE、天赋 TLT、已发生事件 EVT。
- **比较**：`>` `<` `>=` `<=`，如 `INT>7`、`MNY<3`。
- **存在性判断**：`对象?[id,...]` = 已发生/已拥有（逗号列表为「任一」）；`对象![id,...]` = 未发生/未拥有。如 `EVT?[10009]`（要求某前置事件已发生）、`TLT?[1005]`（要求持有某天赋）、`AGE![500]`（年龄不等于 500）。
- **逻辑组合**：`&`（且）、`|`（或）、`()`（括号分组），可任意嵌套，如 `(EVT?[10009])&(STR<3)&(SPR<3)`。

按条件类型归类，各举 2 例（仅引用条件写法，正文不引）：

1. **年龄条件**：`AGE?[30]`（恰在 30 岁，天赋「三十而立」式触发）；branch 中 `AGE![500]`（非 500 岁才走此分支）。
2. **属性阈值条件**：include `INT>8`（高智力才可能被随机到）；branch `STR<2&MNY<3`（体质与家境双低 → 跳转到死亡事件）。
3. **前置事件条件（include）**：`EVT?[10009]`（必须经历过「农村出身」事件，其后续事件才解锁）；`(EVT?[10101])&(INT>7)`（上过学且智力高）。
4. **互斥/防重复条件（exclude）**：`EVT?[自己ID]` 是最常见的写法——事件把自己写进 exclude，实现「一生只发生一次」；`EVT?[10007,10008]` 两个姊妹事件互相排除，只会出现其一。
5. **天赋条件**：include `TLT?[1005]`（持有某天赋才解锁专属日常）；branch `TLT?[1016]:目标ID`（有救生类天赋则落水不死，跳转到获救事件）。
6. **复合否定**：exclude `(EVT?[若干])|(TLT?[若干])`——发生过任一相关事件或持有冲突天赋都排除。

### 1.5 「分支」到底是什么：系统判定分支，不是玩家选项

这是最容易误学的一点：lifeRestart **没有玩家选项**。它的 branch 是事件结算后由系统按条件自动跳转的**链式后续**（如重病 → 有玉佩天赋则活下来 / 体质家境双低则死亡）。链条节点用 NoRandom 标记、只进不出随机池。它的「花样」来自：条件网 + 链 + 年龄池权重，而不是选择。

对《如果那年》的取舍：我们的分岔是玩家主动选择（已有 flags 系统），应保留；可借的是它另外三件——①前置/互斥条件的统一表达式思路（我们的 require/forbid 是其简化版，可扩展属性阈值与「已发生事件」两类）；②链式事件用「不进随机池、只由前置带入」管理（我们的回响事件可改用此式，避免被随机池稀释）；③postEvent 式的「后果补述句」字段，正对应我们已落地的 echo 回响。

### 1.6 结构结论（给扩库工程的清单）

1. 总量靠「年龄池重叠复用」放大：1562 条事件、每岁约百条候选，单局实际只见约 80–100 条——重玩差异来自池大，不是单局内容多。
2. 一次性事件不靠引擎特判，靠 exclude 写自己；姊妹互斥同理。写库规范比引擎功能更重要。
3. 条件只用一套 DSL 贯穿 include/exclude/branch/天赋四处，作者只学一种写法——这是它能靠人力堆到 1500+ 的关键工程原因。
4. 内容生产是表格驱动（xlsx → json），非程序员可填表扩库；我们后续扩到 500+ 时应同样走「表格/结构化文本 → 数据文件」的流水线。
5. 稀有度只有 4 档（grade）+ 权重一维调节，不做好几套概率系统。

## 二、时代大事件清单（56 条）

读法：每条 = 年代区间（历史锚点）｜普通人被卷入的方式（一句）｜建议放入的年龄段。
主角毕业年份不固定，下表年龄段按「浪潮打到普通人时的人生阶段」给：一局 43 年里建议只锚 2–3 条为必经浪潮，其余作同代背景事件抽选，避免一局变新闻联播。

### 就业与行业周期（1–14）

1. **高校扩招后的毕业生洪峰**（1999 扩招，毕业生人数此后一路攀升至 1200 万+/年）｜毕业即内卷，第一份工作靠抢、起薪被压。｜22–24
2. **2008 金融危机与四万亿**（2008–2010）｜外贸制造业订单骤减、农民工返乡潮；或恰好踩中基建与地产风口。｜22–28
3. **互联网大厂扩张黄金期**（2010–2018）｜校招高薪与期权造富故事，同学间收入差距第一次拉开。｜22–30
4. **移动互联网创业潮 / 大众创业万众创新**（2014–2018）｜同事辞职创业、共享单车式风口起落。｜24–33
5. **新能源汽车产业链风口**（2019 起）｜传统车企人跳槽去新势力，工资翻倍或站错队。｜24–36
6. **半导体国产替代 / 硬科技风口**（2019 起）｜工科生被高薪挖角，行业从冷门变显学。｜22–32
7. **跨境电商风口**（2020 起）｜外贸业务员转行做跨境，账号被封一夜归零的也有。｜24–36

## 三、建议的事件分类体系（供 500–1000 条扩库使用）

按「玩家感知」而非「数据来源」分类；每条事件除主类外可带横切标签（路线限定 / flags 前置 / 属性阈值 / 一次性 / 影子线）。

| # | 类别 | 一句话 | 目标占比参考 |
|---|---|---|---|
| 1 | 时代浪潮 | 大事件落到一个人身上的切面：风口、危机、政策转向，每局必经 2–3 条锚定，其余抽选。 | ~8% |
| 2 | 职业生计 | 入职、跳槽、晋升、裁员、转行、副业——钱从哪来就写哪。 | ~18% |
