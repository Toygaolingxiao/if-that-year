# 扩展与负载架构：人再多，也先轮不到「负载均衡」

> 用户问题（2026-10-30）：做成网页后，大量人同时用，服务器怎么做负载平衡？
> 结论先行：**按本书的架构，前三级扩容根本不需要自己做负载均衡。** 因为游戏不在服务器上运行——它在玩家的浏览器里运行。服务器只负责把一份静态文件发出去，这件事由 CDN（内容分发网络）在全球边缘节点完成。真正需要均衡的，是后期少数几个后端功能（支付、投稿、生成 PDF），那些用无服务器函数 + 托管数据库解决，按量自动扩缩，不养常驻服务器。

## 1. 为什么这个游戏天然抗流量

一局游戏的全部运算：种子随机数、事件抽取、数值增减、影子线推演、分享卡绘制（Canvas）。
这五件事全部在浏览器本地完成（确定性引擎，见设计书 §11）。服务器在整局里只参与一次：**把页面和事件库 JSON 发给玩家**。之后玩家点 200 次，服务器的负载都是 0。

对比：如果按「每次选择都调一次大模型」的架构做，一局 40 次调用、10 万人同时玩就是 400 万次推理请求——那才是会熔断、会烧钱的架构。本项目在设计书里就把这条路堵死了（在线零 LLM 调用），负载问题在架构层已经被解决大半，剩下的只是分发问题。

## 2. 分级扩容路线（每一级都有触发条件，不提前买）

### L0 起步：Cloudflare Pages（当前阶段，2026-10-30 用户拍板直接采用，跳过 GitHub Pages）
- 形态：Cloudflare Pages 连 GitHub 仓库，推 main 自动部署，全球边缘 CDN 分发。仓库私有不影响部署，站点经 pages.dev 公开（仓库接入尚待用户在 Cloudflare 后台完成，站点未上线）。
- 接入步骤与排障见 `docs/DEPLOY-CLOUDFLARE.md`；缓存规则在仓库根 `_headers`。
- 带宽量级参考：一局首屏约 300–600KB（gzip 后），静态分发的成本在百万次访问量级前都接近零；各家免费额度与条款上线时复核，不把「免费无限」写进承诺。

### L1 扩容：仍在 Cloudflare 内解决（原 GitHub Pages 路线废弃，仅留作备选知识）
- 触发条件：Pages 额度接近上限，或需要更细的缓存/安全规则（WAF、Bot 管理——账号里 komesomme.jp 已有同类功能经验）。
- 做法：仍是同一份静态文件，靠提高边缘缓存命中率扛量——静态资源设长缓存 + 文件名带哈希，事件库 JSON 设短缓存以便更新；访客就近取边缘节点的文件，源站几乎不被直接访问。这一级理论上可承受百万级日访，成本仍接近零到每月几美元量级（各家免费额度与条款上线时复核，不把「免费无限」写进承诺）。
- 这一级就是通常意义上的「负载均衡」：不是我们买几台服务器做均衡，而是 CDN 天生把请求分散到全球节点。

### L2 需要后端时：无服务器函数，只加四个口子
触发条件：上线珍藏付费、故事墙、短链、埋点中的任何一个。
- 计算：Cloudflare Workers / Vercel Functions 一类无服务器函数——请求来了才运行、按次计费、平台自动在全球扩缩，没有「服务器数量」这个概念，也就没有手工负载均衡。
- 四个口子各自独立，互不拖累：①支付回调（Stripe，量极小）②珍藏 PDF/海报生成（异步排队生成，生成完给下载链接，不让玩家等在同步请求里）③故事投稿与审核（低频）④匿名埋点（可先用现成隐私友好统计服务，连自建都省了）。
- 数据库：托管型（Supabase / Cloudflare D1 等），自带连接池与备份；本项目数据量极小（投稿、订单、种子短链），单实例托管库可撑很久，先不谈分库分表——那是日活千万级产品的问题，提前做就是浪费。

### L3 真爆了之后：降级与保命设计（先写进代码，不先花钱）
- **静态保底**：任何后端故障时，游戏本体照常可玩（纯前端），坏的只是支付/投稿——把故障半径锁死在非核心功能里。
- **限流与排队**：PDF 生成、定制局生成等重活走队列，宁可慢，不可崩；接口加基础限流防刷。
- **成本护栏**：所有按量计费的服务设月度预算告警（设计书 §12 的 ¥100,000 现金上限口径下尤其重要）；LLM 只用于离线内容生产，调用量与在线人数完全脱钩。
- **可观测**：只看四个数——首屏成功率、完局率、分享率、付费转化。后端错误率告警到邮件即可，不上复杂监控系统。

## 3. 一张表看懂「人多时会发生什么」

| 同时在线量级 | 瓶颈在哪 | 我们的状态 |
|---|---|---|
| 100 人 | 无 | Cloudflare Pages 裸奔 |
| 1 万人/天 | 首屏带宽 | Pages 免费额度内从容应对 |
| 100 万人/天 | CDN 缓存命中率、事件库 JSON 体积 | Cloudflare 边缘缓存，源站无感；JSON 拆分按需加载 |
| 爆发峰值（如上热搜） | 支付/PDF 等后端小口子 | 无服务器自动扩缩 + 异步队列；游戏本体不受影响 |
| 恶意刷量 | 带宽与接口滥用 | CDN 层限流 + 预算告警，最坏情况只是账单预警，不是宕机 |

## 4. 明确不做的事
- 不自建服务器、不租云主机养常驻进程、不做 Nginx 负载均衡配置——在这个体量和形态下，那是给自己制造运维和账单。
- 不把存档放服务器（本地 localStorage），省掉账号系统、数据库和隐私风险三件事。
- 不做实时多人（双人局是同设备轮流），省掉 WebSocket 长连接这一整类负载问题。
