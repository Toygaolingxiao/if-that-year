# v0.21 施工蓝图：平行人生与交换人生

定性与形状以 `docs/SWAP-LIFE-DESIGN.md`（创始人定案，2026-11-03）为准，本蓝图只解决「怎么建」。交换时机按 **A+ 案**施工（30/40/50 三个瞥视点都问、一生最多换一次、机会状态对玩家明示）。2026-11-03 21:58 的系统设计评审六条已由主代理裁定采纳，本蓝图已逐条按新口径修订：政策纯函数化、交换改控制权交接、接管容错、瞥视信息两层标准、早夭无保底、时机 A+ 定案；设计稿的对应改法见文末第十一节。

## 〇、硬约束（任何一条破了都不算完工）

1. **老种子主线复现不许破**：同一主种子在 v0.20.3 与 v0.21（一期）下，主线人生的账本与流水逐字一致（不换的局，二期同样要求全程一致；换的局要求交换年之前一致）。实现靠第二节裁定一、二，验收靠第八节的 parity 套件。
2. **主线既有护栏零倒退**：quality-gate 全套（双校验、状态线断言、链选择、结算对账、确定性 200/200、旧档可读、职业对账、阈值、特殊总率 ≤13%、传说/史诗单体 ≤1%、死亡年代带、零命中不净增）在一期收尾时与 v0.20.3 终数逐项同值（parity 成立则主批数字应天然全等，有差即缺陷）。
3. **信息两层不破**：瞥视披露只有事实层（婚否、房贷/债务、体检异常提示、子女有无、居所大类等真实事实，无数字）；数值层（六维、金额、账本全文）永不出现；预后层（过得好不好、换了赚不赚）永不评价。细则见第六节。
4. **不卖更好的人生**：影子与主线同分布、同规则、同死亡模型；政策全文公示，不给影子任何隐藏优待或惩罚——**包括不设隐形保底**：不许偷改影子的死亡分布让它活到瞥视点（理由见 6.3），它的早夭是对玩家诚实的一部分。
5. **存档只加字段不改义**：老存档可读可玩完（无 Track_B 的局走旧模板瞥视回落路径，见 3.3）。
6. **政策纯函数（硬卡点）**：「另一个你」是无状态纯函数 `Action = F(State, Personality_Vector, Route_Bias)`——无内部概率抖动、无隐藏状态、不读三入参以外的任何东西（不抽随机流、不读全局计数、不读另一条 Track）。验收升格为单元级：同一 MainSeed 下影子 LifeRecord 逐字节复现（见 4.0 与 8.1）。
7. **交换零搬运**：交换只移交控制权（裁定一），两条 Track 的状态数据一字不动、模拟层一字不互读；任何「对调字段」的实现都算违例。

## 一、现状锚点（施工前先认清的代码事实）

- **引擎是单例状态**：全部决策层函数（`met`/`ctxOk`/`factOk`/`evidenceCount`/`planYear`/各进程 due/`applyState`/`applyEffects`/`rec`）只读全局 `IFY.S` 与三个流状态对象 `RNG/RNGW/RNGA`（`{a}` 计数器，engine.js）。呈现层（render*）才碰 DOM。这是本轮最大的结构事实：影子人生的全部可行性建立在「决策层与呈现层已分离」之上，不需要、也不许做参数化重构。
- **随机流分家（v0.18）**：`seedStreams(seedStr)` 派生三股——叙事流 `H(seed)`、进程流 `H(seed+"#world")`、环境流 `H(seed+"#ambient")`；序章流 `H(seed+"#prologue")` 在 prologue.js 内；出身牌流 `H(seed+"::cards::*")` 在 cards.js 内。主种子派生方式一字不动是硬约束 1 的根。
- **存档**：`save()` 把 `{...IFY.S, rngA: RNG.a, rngW: RNGW.a, rngAmb: RNGA.a}` 写进 `ify-save-v2`（注意存档键 `rngA` 存的是叙事流 `RNG.a`、`rngAmb` 存环境流，命名是历史包袱，照旧）。续玩回填在开局页 resume 处理器里逐字段补缺——新字段按同一口径加回填行。
- **年循环时序（step/advance）**：进程拍（父母 → dating → 出国去向 → 退休相位）→ 分岔 → 瞥视（`GLIMPSE_AGES={30:0,40:1,50:2}`）→ `planYear()` 内容时槽（L1 危机 → L2 稀有/链/考试链头 → 温度平淡年 → L3 saliency → L4 微年）。`advance()`：年龄 +1 → `rollDeath()`（进程流）→ `step()`。
- **父母进程**：`initParents()` 在首个有路线的 step 里惰性掷点（进程流三角扰动）：`age0`（父母生主角时的年龄）、`deathAge/careAge/hospAge`（换算成主角年龄口径）；`parentsDue()` 每年至多一件，优先级 离世 > 住院 > 照护 > 预警信号。
- **死亡模型**：`rollDeath()` 意外线 + 健康线 λ = a(年代）·g^(age−40)·hf（健康），参数在 `MORTALITY_BY_ERA`；死因文本按本局事实过滤（v0.20.1）。
- **账本**：`rec(kind,id,extra)` 写 `{age, kind, id, choice?, set?, fx?, text?}` 进 `S.ledger`，`flagAges` 随 set 落点。结算九槽、证据、道路图都读账本（settlement.js 的 `settlementSlots/specialEnding/chosenOfFork/nearMisses/settlementMapHtml`）。
- **现行影子（模板版）**：`D.shadows[routeId] = {name, teaser[3], stages[3][4], cost[3]}`；对象路线 = `S.unchosen` 里第一条 route 条目（newGame 与 mergeIntoRoute 都按 `D.routes` 原序写入，口径一致）；`shadowStageText()` 每次瞥视渲染恰好消费叙事流 1 抽；结算第八槽（另一条路）与 `shadowCompareLines()` 读模板的 cost/final 文本。瞥视里已有：先标题后细节、看/不看计数（真的）、反思认领输入（→ `S.reflections` → 结算第九槽）、第一次瞥视的机制说明、童年记号共同事实句。
- **模拟口径**：sim（sim-v0203/scripts/sim.js）以 VM 按 index.html 顺序载入真实代码、自备主循环复刻 step/advance 语义、人格选择走独立玩家流不耗游戏流；模式 main/determinism/regression/audit/oldsave。实测锚点（本机 VM）：`main 100`（每代 100 局、共 400 局）约 33.6 秒墙钟，固定加载与审计仪表占大头——每局边际成本由 WP1 用微基准另测（见第九节），不许拿这个总数当单局成本报。

## 二、核心机制三裁定

### 裁定一：双 Track 完全解耦 + 控制权指针（不做参数化重构）

模型（2026-11-03 评审定案，取代初稿的「影子挂主存档 + 字段对调」思路）：22 岁分岔起存在两条 **Track**——Track_A（玩家选的路线）与 Track_B（没选的那条主打路线）。两条 Track 自出生起完全解耦：各自一份完整人生状态、各自的 NPC 状态表（父母、各进程状态都长在各自 state 里）、各自的随机流子状态，**模拟层零交叉读取**——一条 Track 的推进永不读另一条的任何字段。玩家「在过」哪条由一个**控制权指针**决定；没被控制的那条由政策 Bot 驱动（第四节）。交换 = 指针移交 + Bot 反向接管，数据零搬运（第七节）。呈现层（瞥视/结算）是只读观察口：它读不受控 Track 的账本呈现给玩家，但不写回任何 Track、不参与任何一边的推进——观察不算耦合。

结构图（即存档的顶层形状，见 3.3）：

```
session（会话层）
├─ controlTrack: "A" | "B"          ← 控制权指针（存档字段）
├─ tracks:
│   ├─ A: { state, streams:{n,w,a}, routeId, memorialShown, finalized }
│   └─ B: { state, streams:{n,w,a}, routeId, memorialShown, finalized } | null（legacy 局）
└─ meta:                            ← 玩家层，不属于任何一条 Track
    { reflections, glimpsesSeen, glimpsesSkipped, autoMode, speed,
      swapped, swap:{age, from, to}, controlLog:[{track, fromAge, toAge}],
      shownFacts:[], policyV }
```

施工形态：新建 `src/world/shadow-life.js` 持有 session 与上下文切换器 `withLife(trackCtx, fn)`——把 `IFY.S` 换成目标 Track 的 state、把 `RNG.a/RNGW.a/RNGA.a` 换成该 Track 的 streams、快照 `IFY.schedStats`，执行 fn，finally 全部还原（含异常路径）。`IFY.S` 在任何时刻都指向**受控 Track** 的 state 对象：全部既有呈现/结算代码读的永远是玩家正在过的那条人生，零感知。受控 Track 的年步进就是现行 step/advance 原样；不受控 Track 的每一年 = 切进去跑一遍无头年步进（第五节）、切出来，决策层代码（调度、进程、状态边、账本、证据）一行不改地复用。不受控上下文中禁止调用：任何 render* 函数、`save()`、`ANA.track`、DOM。加开发断言：`IFY._lifeDepth` 计数，`save()` 在 depth>0 时在 sim/调试口径下报错（防施工手滑）。切换纪律：任何缓存了 `IFY.S` 引用的代码不许跨交接存活，交接后必须重读 `IFY.S`（7.2）。

`tracks.B == null` 即「无 Track_B 局」（老存档续玩，见 3.3 回填口径）——全游戏只有三处读 session 结构：`advance()` 的不受控步进钩子、瞥视视图、（二期）结算段视图与控制权交接。其余主线代码不许分支读它（parity 的结构保证）。

### 裁定二：#shadow 三子流，主线四流一字不动

```js
seedShadowStreams(seedStr):            // 只给 Track_B 派生；Track_A 用现行四股，不动
  n = H(seedStr + "#shadow")            // Track_B 叙事流（保留派生；政策禁用，见下）
  w = H(seedStr + "#shadow#world")      // Track_B 进程流（父母掷点、死亡、退休 part 年数、死因文本挑选）
  a = H(seedStr + "#shadow#ambient")    // Track_B 环境流（planYear 全部抽取）
```

后缀方案与现行 `#world/#ambient` 同构。主线三股与序章流的派生输入不变 ⇒ 其数值不变是构造性的，不是测出来的。每条 Track 只许消费自己的流（withLife 切换保证）；Track_A 将来被 Bot 驱动时用的仍是它自己那三股主线流（计数器存在它自己的 Track 条目里），不新派生。**政策不消费任何流**（硬约束 6）：并列决胜靠确定性全序（4.3 第 4 级）；Track_B 叙事流目前在无头步进里没有消费者，派生保留只为流族完整，政策永不许碰它。

**parity 的第二个条件在呈现层**：现行 `renderGlimpse` 每次渲染经 `shadowStageText()` 恰好消费叙事流 1 抽。新瞥视（第六节）保留这个不变式——主素材选取出现并列第一时，用恰好 1 抽叙事流决胜；无并列时也消费 1 抽（抽了不用，丢弃）——使瞥视年主线叙事流的相位与 v0.20.3 逐位一致。此不变式写进代码注释并由 parity 套件守着，任何人改瞥视呈现都先过这条。

### 裁定三：父母——出身共享，命运各自

- **共享**：`age0`（父母生主角时的年龄）。这是分岔之前就成立的家庭事实，同一个人、同一个家。影子出生时从主线 `S.parents` 直接拷贝，不掷点。
- **各自**：`deathAge / careAge / hospAge`（及 signal 派生）在影子进程流上按同一 `PARENT_CAL` 与同一公式重掷。
- **理由**：① 防泄漏——若共享 deathAge，瞥视里「那边爸爸走了」就等于预告玩家自己这一生的父母离世年，信息不全当场破功，而且那是假话：影子的人生里父亲的离世不携带主线的信息；② 贴题——离父母远近正是路线之间最真实的差异之一（回家乡线与出国线的父母线本就该长得不一样），共享轨迹反而把路线的分量抹了；③ 与地基 §3.6 同口径——影子只挂选择，分岔之前是同一个人，分岔之后连世界给他的遭遇都各自走（事件抽取本就各自独立，父母进程没有理由例外）。
- **施工注**：主线 `initParents()` 现在是惰性首 step 触发；Track_B 出生需要 age0，故在 `newGame()` / `mergeIntoRoute()` 落路线后、首次 `save()` 之前显式调用一次 `IFY.initParents()`。已核：22 岁首个 step 之前进程流没有任何其他消费者（rollDeath 在 30/40 岁前不掷、applyState 的 workPhase 掷点只在流转时），调用点前移不改变进程流的消费顺序，parity 套件复核。parents.js 的掷点函数 `one()` 改为可注入流抽取函数（Track_A 传 rngW、Track_B 传它的 w 流包装），公式与标定不动。（出生时拷 age0 是分岔构造的一次性动作，不是运行期交叉读取：22 岁之后两条 Track 再无任何数据往来，见裁定一。）

**年代锚点裁定**（连带）：日历共享、抽取独立。`src/anchors.js` 是只读登记表、`planYear` 的年代池按公历年开门——两条人生同年代同出生年，日历天然一致，不需要任何「共享世界状态」；时代事件在各自人生里各抽各的实例。引擎现状本就没有全局可变世界状态，此裁定只是把事实写明，零施工。

## 三、状态与存储（问题 1）

### 3.1 Track_B 的状态：与 Track_A 整表同形，玩家层字段不在 Track 里

Track_B 的 state 由 `freshState(seedStr)` 同路径生成后改路线落值——两条 Track 同形是裁定一的构造要求（玩家与 Bot 要能在任一 Track 上无差别地驱动同一年步进）。字段处置逐项如下（不列即整表复用）：

| 处置 | 字段 |
|---|---|
| **同值拷贝自出生点**（分岔之前的同一个人） | `seedStr / era / birthYear`（恒等）；序章年代：`state.schooling / state.track`、`marks`、`prologue` 里的处境/性子/家底/时代结论（`situation/temperPick/family/eraCard`，运行态字段如 stage 指针不拷）；卡牌年代：`cards`（玩家所选三张，与主线同——出身是发的与选的都已在 22 岁前落定） |
| **按 Track_B 路线重走** | `route`（Track_B 的路线）、`stats`（初值 → 同一批出身牌 effects → Track_B 路线 route.stats，叠加顺序与 newGame 一致）、`temp/rhythm`（Track_B 路线的 `rhythmBase("route", …)`）、`unchosen`（Track_B 自己的：它的路线是选中的，其余四条入它的 unchosen；它在各分岔的不选支照常在它自己的账本里记账累积） |
| **独立一份、各活各的** | `state`（十域全独立）、`flags/flagAges`、`ledger`、`log`、`usedEvents/usedRare/microUsed/crisisUsed`、`parents`（按裁定三）、`datingSince/datingDefers`、`kidsAt/kidsBornAt/catAt/dogAt`、`retirePlan/partAt/partYears/retiredAt/retireDefers`、`covenant`、`healthCrisisSeen`、`death`、`flatCarry/flatYears`（质地计数随人生走） |
| **不在 Track 里（玩家层）** | `reflections`、`glimpsesSeen/glimpsesSkipped`、`autoMode/speed` 归 session.meta（裁定一结构图）——它们是玩家的话、观看史与偏好，不是任何一条人生的状态；现行读这几处的主线代码（结算第九槽、瞥视计数、推进设置）改读 meta。Track 的 state 里保留同名字段只为同形、恒不作数（施工时在字段处注释标明）。`pendingFork` 是呈现挂起位，不受控 Track 恒为 null（无头步进内联解决分岔，永不挂起） |
| **Track 专有** | 无——专有状态全在 Track 条目外层（routeId/streams/memorialShown/finalized），state 本身两条 Track 完全同形。这是刻意的：同形 + 零搬运，控制权交接（第七节）才不需要任何字段映射表。 |

### 3.2 账本：同构、独立、互不串写

每条 Track 的账本就是它自己 state 里的 `ledger` 数组，条目形状两条 Track 一字不差（`{age, kind, id, choice?, set?, fx?, text?}`），`rec()` 在 withLife 内调用即写入当前 Track 的账本（`flagAges` 同理）。`log` 流水同理各一份（瞥视取材与悼念的文本来源，见第六节）。两本账互不写入；唯一的「同一年两边都记」是二期交接时由交接程序在各自上下文里各落一条 `kind:"swap"` 标记（只含路线名与岁数，是记账不是搬运，见 7.2）。校验侧：`validate-state` 的账本检查对两条 Track 同口径适用，WP1 把它接进 quality-gate 的双 Track 样本检查（随机抽 N 局、两本账都跑同套断言）。

### 3.3 存档形态（双 Track 并存）与老存档回填口径

- **写入**：`save()` 改为序列化 session（裁定一结构图），仍写 `ify-save-v2` 键，形状内带版本号：`{ v: 2, controlTrack: "A"|"B", tracks: { A: { …state 字段, rngA, rngW, rngAmb }, B: { …state 字段, rngA, rngW, rngAmb } | null }, meta: { … } }`。每条 Track 条目沿用现行存档口径（state 字段平铺 + 它自己的三键流计数器——Track_A 的三键就是现行主存档那三键，口径不变；Track_B 的三键装它的 #shadow 子流计数）。玩家层字段只存 meta 一份。存档体积约翻倍（多一条 Track 的 log+ledger），量级仍在 localStorage 配额的零头，施工时实测一局终局存档字节数并记进报告。
- **出生时机**：Track_B 在落路线的那一拍出生（`newGame()` 与 `mergeIntoRoute()` 内、首次 `save()` 之前），保证「有路线的 v2 存档必有两条 Track」。
- **老存档回填**（开局页 resume 处理器识别两种形状）：
  - 旧形状（无 `tracks` 字段，即 v0.20.3 及更早的平铺档）→ 就地包成 session：旧 state = Track_A、`controlTrack = "A"`、`tracks.B = null`、meta 按缺省补齐（reflections/glimpsesSeen/glimpsesSkipped/autoMode/speed 从旧 state 的同名字段接过来——它们本来就存在旧档里）。本局按无 Track_B 局玩完：瞥视走旧模板路径（`D.shadows` 数据与现行 shadow.js 逻辑保留为 legacy 分支）、结算第八槽与对照行照旧。**不许中途补生 Track_B**——22 岁已经过去，补生等于编造一段没活过的平行人生，与设计稿「如实呈现」相悖。
  - v2 形状但缺子字段（只会是本轮开发期内的档）：按 session 定义逐项补缺（Track 条目的 `memorialShown/finalized` 缺省 false、meta 的 `controlLog/shownFacts` 缺省 []、`policyV` 缺省 1）。
  - 序章段存档（无 route）：`tracks.B = null`，汇入 22 岁时正常出生 Track_B，与新局同路径。
- **每日一局/分享链接**：Track_B 只由 seedStr 派生，与主线同理——每日局人人同两条人生，分享链接同种子同两条人生，不需要新参数。

## 四、「另一个你」决策政策（问题 2）

政策是代码 + 一份公示文档（新建 `docs/SHADOW-POLICY.md`，玩家可读版：把下面四条讲成人话）。政策只作用于「当前不受控的那条 Track」，只读那条 Track 自己的状态。`policyV=1` 记进 meta；政策改版 = 升 policyV 并在 DEVLOG 记明（单局确定性以「同构建内」为口径，与历轮一致）。

### 4.0 纯函数定义（硬卡点，先于一切权重）

政策是一个无状态纯函数：

```
Action = F(State, Personality_Vector, Route_Bias)
```

- **入参只有三个**：该 Track 当前的完整状态（State）、性子向量（Personality_Vector，4.1）、路线倾向（Route_Bias，4.2）。F 不读时钟、不读全局计数、不读另一条 Track、不读玩家在另一条 Track 上的任何选择史。
- **无内部随机**：不抽任何随机流、不调 `Math.random`、不靠调用次数或迭代顺序决胜。并列的决胜是入参的确定性函数（4.3 第 4 级），同一入参永远同一出参——跨调用、跨进程、跨设备都成立。
- **无隐藏状态**：F 不许带记忆（它上次选过什么不影响这次，除非那件事已经写进 State 本身——写进 State 的就是人生事实，可以用）。实现纪律：政策模块不许有模块级可变状态；按入参键的备忘缓存也不许开（缓存是隐藏状态的风险面，且无必要——F 每年每 Track 至多跑几次）。
- **可单测**：每个抉择点可独立喂入构造状态断言出参，不需要跑整局（4.4 单元门）；这也是 4.5 接管容错成立的前提——Bot 接管任何状态，都只是「把那个状态喂给 F」。
- （定位说明：整条不受控 Track 的逐字节复现 = 流派生确定性 + F 纯函数，两者缺一不可。调度层的抽取本来就由种子定死，能引入不可复现因素的只有政策自己——这正是本条升格为硬卡点的原因。）

### 4.1 性子底色：从玩家选定的性子牌读

- 来源：序章年代 = `S.prologue.temperPick`（童年性子拍的真选择）；卡牌年代 = `S.cards` 里的性子牌 id。两边都是玩家亲手选的「这个人是什么性子」，影子与主线同源拷贝。万一缺失（理论不可达）→ 中性向量兜底并记 sim 警告。
- 形状：16 张性子牌逐张配一个六维权重向量 `W[temperId] = {health, money, growth, freedom, relation, wisdom}`（0–3 浮点）。施工纪律：每张牌的向量必须能从牌面文字里指出依据（一牌一行理由写进 SHADOW-POLICY.md），不许凭手感乱配；配完用影子分布验收（第八节）复核没有哪张性子把影子推成必死/必富的极端。

### 4.2 路线倾向：路线自己的引力

每条路线一份倾向：六维亲和向量 `A[routeId]`（corp 偏 money/growth、home 偏 relation/health、abroad 偏 freedom/growth、study 偏 growth/wisdom、gap 偏 freedom/health——施工时按各路线 route.stats 的签名与路线文本定值，写进政策文档）+ 具名立场表（只列政策文档里说得出口的立场，如 home 路线在 fork28「出不出去」上偏向留、abroad 路线在照护分岔上偏向请人/轮换——逐条与路线文本对得上才许入表）。

### 4.3 选择算法（确定性，四级瀑布）

不受控 Track 每遇到一个抉择点（分岔 / 进程拍选项 / 事件·稀有·危机选项），F 按序求值：

1. **具名分岔规则**（只覆盖大分岔，逐条写死、逐条公示）：`POLICY.forks[forkId]` 是有序规则表，每条 = （该 Track 的状态/数值条件 → 指向某个选项的匹配子）。大分岔清单 = 现行 D.forks 全部（25/28/31/33/38/44/45/52/58，含 fork45 的浮动窗与立约到期——门的成立与否由 `met()` 在该 Track 上下文里同口径判定，政策只在「门开了、选项摆出来了」之后做选择）。规则的写法纪律：每条规则必须是一句能印在政策文档里的话（如 fork31：「看重关系（W.relation≥2）且当下关系不低的人，会把那个人留下来」）；规则之间不许互相矛盾（施工时逐 fork 做规则互斥自查）。
2. **立场加成**：选项命中 4.2 立场表声明的条目 → 按表加分。
3. **性子打分**：`score(c) = Σ_k (W[temper][k] + A[route][k]) · Δstat_k(c)`，Δ 取选项的 effects（与 sim 人格 chooseIdx 同族公式，但权重来自本局的性子牌与影子路线，不是模拟人格）。立约/推迟类机制选项（deferDating/deferRetire）另有硬规则：每条线一生至多推迟一次（与真人分寸对齐，也防政策把 dating/退休无限拖延出怪局）。
4. **并列决胜（确定性全序，零随机）**：打分后仍在并列带内（与最高分差 < 0.5）时，依次用入参的确定性次序打破：① 正向对齐分 `Σ_k W_total[k]·max(0, Δstat_k)` 大者胜（更贴性子想要的）；② 负向规避分 `Σ_k W_total[k]·min(0, Δstat_k)` 大者胜（伤到性子在乎的维度更少）；③ 选项下标小者胜（稳定排序的最后兜底）。三级都是 (State, W, A) 的纯函数——「性子里的犹豫」最终由性子本身裁断，不由骰子。本级是 4.0 的直接落实：政策全程零流消费。

平年事件的「抽哪件」不在政策里——那是调度层的事：不受控 Track 的年步进直接调 `planYear()`（该 Track 上下文 + 它自己的环境流），与受控 Track 同一调度器、同一五层仲裁、同一温度 derive（温度读该 Track 自己的 temp/rhythm）。政策只管「抽中之后怎么选」，不管「抽中什么」。这是刻意的分工：人生际遇的分布由世界规则定（且由种子定死、可复现），性子只决定面对际遇的态度——与玩家侧「抽到什么不由玩家定、怎么选由玩家定」严格同构。

### 4.4 政策验收口径

- **单元门（硬卡点）**：F 的单元测试集——为每个大分岔与每类抉择构造代表性状态（含边界状态），断言：同一入参连调 100 次出参不变；换进程重启后出参不变；入参深拷贝后出参不变（防 F 偷改入参或依赖对象身份）。任一失败 = 政策实现里藏了隐藏状态或随机源，一期不许收尾。
- **逐字节复现门**：同一 MainSeed 下，两次独立整局运行产出的不受控 Track LifeRecord（账本 + 流水 + 终局状态）逐字节全等（与 8.1 第 3 条同一道门，政策侧在此登记为 F 的责任）。
- 全文可公示：SHADOW-POLICY.md 写完后，任一不受控 Track 分岔的选择都能由「规则条文 + 当时状态」复算出来（sim 里给政策加审计模式：输出每个抉择的命中规则号/打分明细，供全记录审计抽查）。
- 分布 sanity：见第八节（影子的婚育/终局分布与主线同量级，不许系统性更顺或更惨——这是红线 4 的可测形状）。

### 4.5 接管容错（Bot 接管玩家过过的人生时）

二期交换后，Bot 接管的是玩家亲手过出的人生——状态可能落在政策自己永远走不出的分布外组合（玩家的选择不受 F 的品味约束）。因为 F 是纯函数，它对任何状态都有定义好的出参；但「有出参」还要逐类写明钳制与兜底，不许靠实现时的偶然行为：

| 决策类 | 分布外情形 | 兜底规则（F 的定义域补全） |
|---|---|---|
| 打分求值 | 六维被玩家推到 0/100 极端、或选项 effects 为空 | 数值先过引擎既有 clamp（0–100）再打分，打分式对任意有限输入恒有定义；全选项并列时走 4.3 第 4 级全序，必有唯一解 |
| 具名分岔规则 | 规则条件读到的组合政策自己产生不了（如立约在身又遇 fork45、丧偶后再婚链中段） | 规则是「命中才生效」的第一匹配表，未命中是正常路径、自动落到立场加成与打分；规则表不许假设任何「不该出现」的状态，施工时逐条规则过一遍「条件字段在极端值下仍可求值」 |
| 推迟类机制 | 玩家已把 dating/退休推迟次数用满、或时钟被拨到边界 | 推迟选项的可见性由既有呈现层同款过滤决定（defers 达上限即不在选项集里），F 只在摆出来的选项里选——无可选推迟 = 不推迟，天然兜底 |
| 立约在身 | covenant 的 kind/到期与 F 的预期不符 | covenant 只是 State 的一部分：分岔门的成立由 `met()` 判定、到期拍由进程层处理，F 不需要「理解」立约——到期那年的选项照常按四级瀑布选 |
| 状态门为空 | 某分岔在该状态下过滤后零个可见选项 | 与呈现层同口径回落（呈现层现行做法：过滤为空则回全选项集），无头解决器镜像同一回落（5.2 清单），F 永远面对非空选项集 |
| 字段缺失/旧形 | 接管的 Track 状态缺本轮新字段 | 接管前先过一遍 3.3 的回填口径（与续玩回填同一段代码），F 只读回填后的完整状态 |
| 已终局 | 接管时目标 Track 已满足死亡/80 条件 | 结构上不可能：交接只发生在瞥视点、且前置条件含「目标 Track 存活未终局」（7.2）；万一数据损坏走到这一步，F 不被调用、该 Track 直接冻结走悼念/结算取材——断言守住，不许静默续跑 |

验收法（进 8.2）：**极端状态接管测试集**——构造一批合成存档（六维全 0 / 全 100、丧偶 + 立约在身 + dating 推迟用满、退休后又遇分岔、父母双亡于 23 岁、子女数在上限、健康危机连发后等，每份先过 `validate-state` 证明是合法状态），把控制权交给 Bot 跑到终局：不抛错、不断链（账本与状态断言全过）、必然终止（死亡或 80）。这批用例与政策单元门一起常设。

## 五、同年推进时序（问题 3）

### 5.1 挂点：advance() 里，主线掷完死亡之后、呈现新一年之前

```
advance():
  受控 Track.age += 1（封顶 80 的现行处理不变）
  if rollDeath() → 受控 Track 终局（不受控 Track 不再步进，冻结在同龄处；二期结算时再快进，见 7.4）
  else:
    stepUncontrolled()     // 新增唯一挂点：withLife(不受控 Track) 内跑它的一年
    step()                 // 受控 Track 新一年呈现（瞥视年读到的对面已是同龄最新状态）
```

不受控 Track 的一年（`stepUncontrolled`，全程在 withLife 内；一期它恒为 Track_B，二期交接后恒为被换下的那条——机制同一份，不分一二期）：

1. 该 Track 的 `age += 1`；它自己的 `rollDeath()`（它自己的进程流 + 同一年代参数表）。掷中 → 落 `death`、记账本与流水，之后年份整体跳过（该 Track 冻结，只等瞥视悼念与结算取材）。
2. 未死且未满 80 → **无头年步进**（`stepYearHeadless`），顺序与 step() 的决策序严格对齐：
   - 父母已在出生时建好，此处只需 `parentsDue()` → 到期进程拍按 5.2 无头解决；dating 到期、出国去向、退休相位同序处理（各 due 函数在该 Track 上下文里原样调用）。
   - 分岔：step() 里那一长串分岔门（含 fork58 与退休进程拍的互锁 `retireDecidedThisYear`、fork52 的 anyParentAlive 等）在该 Track 上下文里同式求值，命中则按 5.2 无头解决（选择由 F 定，第四节）。
   - 瞥视：**跳过**——不受控 Track 不瞥视任何人，它就是被瞥视的那个。反思、自动推进、呈现一概没有。
   - `planYear()` → 按计划 kind 无头解决（crisis/rare/event/flat/micro）。
3. 80 岁封顶与受控 Track 同口径（age 停在 80、不再步进）。

为什么挂在这里而不是 step() 开头：瞥视发生在 step() 的呈现阶段，玩家在 N 岁看到的对面必须已经「活到 N 岁」——它的 N−1→N 这一年（含它在 N 岁的死亡掷点）要在瞥视渲染之前完成；同时挂点之后受控 Track 本年的任何流消费都还没开始，不受控步进只碰它自己的流，parity 不受挂点位置影响（分开计数器本就互不相干，位置只关乎呈现正确性）。

### 5.2 无头解决：与呈现层同一笔账，只是不画

`stepYearHeadless` 的每种条目都按对应 render* 函数的**状态变更清单**逐项镜像（施工时以三份清单对盘：renderProcItem / renderFork / renderEventYear+renderRare+renderCrisis 的变更点）：

- 通用：`applyState(item)`、`item.set` 立旗、无选项时 `applyEffects(item.effects)`、`rec(对应 kind, item.id, …)`、流水一行（文本走 `procText/formText` 同一变体解析——该 Track 流水里的句子必须与它「真呈现时」会出现的句子一致，瞥视取材直接引流水，见第六节）。
- 有选项：政策选定 → `applyEffects(c.effects)`、c.set 立旗、`applyState(c)`、`rec(…, {choice: labelText(c), set, fx})`；分岔另加：`applyTempDelta(c.temp)`、fork38 走 `registerCovenant(c)`、未选支 push 进影子自己的 `unchosen`（kind:"fork"）、标题流水行同 renderFork 口径。
- 进程拍专有机制照走：deferDating 的时钟回拨、deferRetire 的节点后移（政策硬规则限制次数，见 4.3）、父母节拍的 stage 推进与 care_stage 旗（renderProcItem 里那段 parents stage 代码抽成共享函数，受控呈现与无头共用一份，不许抄两份）。
- 稀有：`usedRare` push 在解决前（与 renderRare 同序）；危机：`crisisUsed` 落记与 effects/选项同 renderCrisis 清单。
- 平淡年/微年：`rec("flat"/"micro", …)` + 流水一行；不受控 Track 没有 flatCarry 的呈现合并（那是呈现屏数账），flatYears 计数照记。

**施工纪律**：无头解决器与呈现层共用「变更清单」这件事要落成代码结构——能抽共享的（如 parents stage 推进、fork 记账）抽成 IFY 函数两边共用；抽不出的（事件年记账）在 shadow-life.js 里逐项对着 year.js 写，并在 WP2 的验收里用「同种子同政策 vs sim 人格驱动呈现路径」的对照局验账本形状同构（见第八节）。

### 5.3 父母与世界在时序里的位置

- 父母：两条 Track 各有一份 parents 对象、各走各的 due（裁定三）。同一年里两边的父母拍互不相干、互不阻塞（受控 Track 一年至多一件是呈现限制，不受控 Track 无头解决不受它影响——它也按自己的 parentsDue 同口径至多一件/年，保持两条人生节奏同构）。
- 年代锚点与时代事件：见第二节末裁定（日历共享、抽取独立），时序上无任何跨人生调用。

## 六、瞥视改读真账（问题 4）

一期把 `src/views/shadow.js` 的取材层换掉，呈现骨架（先标题、看/不看、计数真实、反思认领、首瞥说明、共同事实句）全部保留。无 Track_B 的 legacy 局整屏走现行模板逻辑（一行不动）。取材对象恒为「当前不受控的那条 Track」——一期是 Track_B，二期交接后是被换下的那条，取材函数不感知区别。

### 6.1 取材窗与候选分级

取材窗 = 不受控 Track 账本中 `age ∈ (上次瞥视岁, 本瞥视岁]` 的条目（30 岁瞥视的窗是 23–30，即出生后到 30）。候选按级排序（级内取最近，同级同龄取后落账者）：

| 级 | 内容 | 出处 kind |
|---|---|---|
| 0 | 它的死亡（窗内发生）→ 整屏转悼念模式（6.3） | `death` |
| 1 | 状态流转：成婚/离异/丧偶、子女落定、父母离世、退休相位流转、宠物到来与离去 | `state` |
| 2 | **对照点**：它在窗内遇到的、与玩家在同一窗内遇到过的同龄分岔（同 fork 年龄）——「你选了 A 的那一年，它选了 B」是瞥视最有分量的一件 | `fork`（与受控 Track 账本 fork 条目按 age 配对——这是呈现层对照，不写回任何 Track） |
| 3 | 其余分岔落点 | `fork` |
| 4 | 稀有际遇 / 数值危机 | `rare` / `crisis` |
| 5 | 父母照护进程拍（care/hosp） | `proc` |

呈现构成（一屏）：**主素材 1 件**（最高级候选，引该 Track 流水原句——那句话在它的账本里有落点年龄可查）＋ **次素材至多 1 件**（不同级的次高候选，可省略）＋ **现状事实表**（6.2）。主素材出现同级同龄并列时按裁定二消费主线叙事流 1 抽决胜（无并列也消费 1 抽丢弃，守流相位；注意这是呈现层的主线流消费，与政策纯函数无关——政策在 Track 侧零流消费）。

出处可查是硬验收：自动检查遍历模拟局的每次瞥视，主/次素材文本必须能在该局不受控 Track 的 `log` 里逐字找到、现状事实表的每一行必须能在它的 `state/ledger` 里对上来源（第八节）。

### 6.2 现状事实表：信息两层标准（评审定案）

瞥视的现状部分是一张**事实表**，不是一句评价。披露分三层，写死：

- **事实层——必须露**：下表五类必露事实 + 既有事实槽，全部从不受控 Track 的账本/状态里读真事，**无一带数字**（不写金额、不写存款、不写六维、不写「还剩 X 年房贷」）。
- **数值层——永不露**：具体金额、六维数值、账本全文、事件 id、概率。
- **预后层——永不写**：不评价它过得好不好，不与玩家自己的现状作高下比较，不暗示换过去是赚是亏。禁用形状：「过得不错/挺惨/顺风顺水/一地鸡毛」类评价词、与受控 Track 并置的比较句（「比你……」开头的一切句式）、任何指向交换决定的劝诱或劝阻。评审语定版：**事实真实，但无预后评估**。

五类必露事实（每类给「来源 → 句形」；否定形也是事实、由权属/状态直接读出，不许推测）：

| 事实 | 来源（不受控 Track） | 句形（示例口径，施工时按 COPY-AND-AI 定稿） |
|---|---|---|
| 婚否 | `state.spouse` 流转 + 账本 state 条目 | 成家了 / 还没成家 / 成过家、离了 / 成过家、对方先走了 |
| 房贷/债务 | 居所权属（居所轨迹）+ 已登记的房贷/债务事实（买房事件与旗标、借贷类事件——施工时盘点内容池，把来源 id 清单写进取材函数注释） | 租住（无自有房贷，此即事实）/ 自有、房贷还着 / 自有、房贷清了 / 有笔债在还；无任何登记来源时只出居所行、不单独出此行（没事实不出，宁缺不编） |
| 体检异常提示 | 健康类危机条目（crisisUsed.health）+ 体检/查出问题类事件 id 清单（同上，施工时登记） | 身体出过警报 / 出过警报、后来没再听说（有后续事实时才许带后半）/ 没听说身体有什么异常（否定形用「没听说」收口——那是瞥视者的信息边界，不是体检结论） |
| 子女有无 | `state.kids` + kidsBornAt | 有了孩子 / 没要孩子 / 还没定（undecided 不出此行） |
| 居所大类 | 居所轨迹（place 进程/定居地流转） | 还在老家 / 在大城市落脚 / 去了海外 / 回了县城 等大类词，不出具体地址 |

另有既有事实槽照旧可出（同样只报事实）：路线与活计（职业轨迹最近一段的大类说法）、父母（都还在 / 还剩一位 / 都送走了）、活计相位（还在干活 / 兼职着 / 退了，只在 part/retired 时出）。排版：事实表逐行短句陈列，不拼成长句评语；每行施工时过一遍「读出声，像不像在转述一个人的近况」——像下结论的，删。

### 6.2b 文案模板规范

- 事实句模板 = 省略主语的转述形，时态只落在「已经发生 / 现在如此」，将来时预言全禁（「以后会……」不许出现）。
- 同一事实全游戏只用一套句形，登记在取材函数旁的措辞表里，不许每次瞥视换着花样说同一件事——花样本身会读出评价感。
- shownFacts 记账：每次瞥视实际呈现的素材（id+age）与事实行（槽名）落进 meta.shownFacts，二期揭价只许对着这份清单选材（7.3）。

### 6.3 悼念模式（对面先走）：正式的一拍，且不设保底

**先把取舍写明（创始人过目点）**：不受控 Track 与受控 Track 同一死亡模型、同一掷点规则，**不设任何隐形保底**——不许为了「让玩家三次瞥视都看得见它」偷偷压低它早年的死亡率。理由：① 这个机制之所以可信，靠的就是对面跟玩家走同一套规则；保底一旦存在（且必然会被玩家从分布里察觉、或从代码里挖出），每一次瞥视都变成表演，交换决策的信息基础整个塌掉；② 早夭本身就是「另一条路」最真实的一种走法，把它抹掉，等于在最要紧的地方对玩家撒谎；③ 靠悼念与结算的重量让短短的一生在游戏里站得住（见下），而不是靠造假让它变长。代价如实登记：可观比例的局里对面会在 30 岁前离开（比例由 8.1 的分布附表单列实测），那些局的瞥视与交换戏份天然变薄——这是诚实的价格。

触发：不受控 Track 已死亡且其条目 `memorialShown == false`（玩家跳过某次瞥视时悼念顺延到下一次，不许被跳过吃掉）。悼念是一屏正式拍，构成（全部取自它账本的真事）：

1. 死讯：它的死亡流水原句（死亡岁数 + 死因文本）。
2. 它这一生的收尾叙述：按年龄序读它账本的 state 流转与分岔落点，挑「出生路线 → 成家与否 → 子女 → 最后一次流转」这条骨架各一句（分级同 6.1、取材窗放宽为全生）——不是报一件素材，是把这一生收成一段。
3. 事实表收尾形：6.2 的事实表按它去世时的状态定格呈现。
4. 静默收口一句（措辞施工时定，口径：只陈述「那条路在 X 岁走完了」，不煽情、不升华）。

呈现后置该 Track 条目的 `memorialShown = true`。此后若还有瞥视点，改为**回望**：只出定格的事实表 + 收尾叙述的第一句，不编新素材、不重复煽情——它的人生已经定格，回望就是看一眼定格的样子。二期口径：悼念屏与回望屏**不出交换提问、不出机会说明行**（人不在了，没什么可换——设计稿定案）。结算侧给足重量在 7.3：第八槽对早夭的对面用同一套全生收尾骨架，不许因为它活得短就只剩一行。

### 6.4 与现行瞥视的衔接清单

- `shadowSeenTexts / shadowFinalText / shadowCostText / shadowCompareLines` 与 `D.shadows` 数据：新局不再消费；仅 legacy（无 Track_B）局继续用。函数保留、入口按有无 Track_B 分流。
- 反思认领：照旧（写 meta.reflections，与两条 Track 无关）。
- 童年记号共同事实句：照旧（首瞥、两条路共同的事实——影子真账与它不冲突，它讲的是分岔之前的事）。
- 瞥视计数（seen/skipped）：照旧真实计数（存 meta）；二期的交换提问与机会说明行挂在「看了」之后（7.1）。

## 七、交换（二期）（问题 5）

### 7.1 提问、机会明示与执行的挂点（时机 A+，定案）

`renderGlimpse` 真账版在玩家点「看」之后、继续按钮之前插入交换提问（仅当：未交换过 `!meta.swapped`、不受控 Track 存活、本次是「看」不是「跳过」、本次不是悼念/回望屏）。按钮两枚：「换过去，过它接下来的日子」/「不换，继续过我的」。拒绝只关本次（下一个瞥视点还问）；接受 → `handControl()`（7.2）→ 照常 advance。提问点 = GLIMPSE_AGES 三岁，一生至多成交一次。

**机会明示（A+ 的「+」）**：只要交换机会还活着（未用掉、对面存活），每次瞥视屏在提问区上方以 hint 级小字安静地放一行：**「换过去的机会，一生只有一次。换了，就再没有第二次。」**（措辞施工时按 COPY-AND-AI 微调，口径不变：只陈述机会的存量，不劝换、不劝留、不评价对面过得如何——预后层禁令在这一行同样生效。）机会用掉之后此行不再出现；对面已去世时不出现（悼念屏口径见 6.3）。「等还是换」的机会成本由此摆到明面，不让玩家在不知情里随手耗掉唯一一次机会。设计稿的时机待定项就此关闭（B 案废弃，不再留配置位）。

### 7.2 交接程序：只动指针，数据零搬运

`handControl()` 的全部动作（顺序写死，每步可断言）：

1. **前置校验**：`controlTrack` 指向当前受控 Track；目标 Track 存在、存活、未终局；`meta.swapped == false`。任一不满足，提问本不该出现，走到这里即断言失败。
2. **记账（玩家层）**：meta 关闭当前 controlLog 段（落 toAge）、开启新段；落 `meta.swap = { age, from: 旧受控路线名, to: 新受控路线名 }`；`meta.swapped = true`。
3. **两本账各记一笔**：在交出 Track 的上下文里给它的账本落 `{kind:"swap", id:"swap_out", age, choice: 对方路线名}`，在接管 Track 的上下文里落 `{kind:"swap", id:"swap_in", …}`——各自记各自经历的这一拍，只写路线名与岁数，不搬任何状态。
4. **翻指针**：`session.controlTrack` 翻到另一条；`IFY.S` 与三股全局流计数器改绑到新受控 Track 的 state 与 streams（每条 Track 的流计数一直存在它自己的条目里，改绑只是把「当前」指向它，数值一字不动）。
5. **存档 + 重呈现**：`save()`；当前年屏幕按新受控 Track 的状态重走呈现——玩家看到的就是他刚接管的这条人生的当年。

**没有字段表**——这是本节与初稿最大的不同，也是控制权模型的全部要点：六维、伴侣、子女、居所、职业、旗标、账本，从来都是各长在各 Track 里的，交接不搬它们中的任何一个；玩家层的 reflections、瞥视计数、shownFacts、机会存量从来都长在 meta 里，交接也不碰。任何实现里出现「把 A 的字段写进 B」的代码，即属违例（硬约束 7）。

**交接之后**：原受控 Track 自下一年起由 `stepUncontrolled()` + 政策 F 驱动（F 的入参 = 那条 Track 自己的 State 与它自己的性子向量——两条 Track 出生时同源拷贝了性子底色，各读各的那份）；玩家侧一切呈现层代码零改动（它们读的 `IFY.S` 已是新人生）。Bot 接管玩家过出状态的容错口径见 4.5。

**确定性口径**（写进政策文档）：每条 Track 的轨迹 = f（种子，它被 F 驱动的年月的 policyV，它被玩家驱动的年月的玩家选择）。交接不改任何一条 Track 的流与政策：Track_A 继续消费 A 的流、由 F 接管；Track_B 从交接年起由玩家选择决定走向、其流的消费序随玩家选择而变——这是特性本身，不是复现性破损：同种子 + 同交接决定 + 同后续选择 ⇒ 同结果，sim 的 determinism 模式按此口径扩（带交接的脚本局双跑比对两本账）。

### 7.3 结算吃两段事实

引入**段事实视图** `IFY.playerFacts()`（settlement.js，二期），段界由 meta.controlLog 给出：未交接时恒等返回受控 Track 自身（结算代码零感知）。交接后：

- **账本视图** = controlLog 各段拼接：每段取该 Track 账本中 `fromAge ≤ age ≤ toAge` 的条目（swap 记账条目是分界碑，相邻两段都含它）。`settlementSlots` 的事实读取（子女/父母/没办完的事三槽与 `hasFact` 类判断）、`specialEnding` 的 evidence、`chosenOfFork`、`nearMisses` 改读段视图。
- **状态类槽**（落脚/陪伴/钱/手艺事业）：读**终局身体**（接管人生的最终 state 与其轨迹）——玩家最后活在哪个身体里，哪里的收场就是他的收场；但手艺事业槽的轨迹跨段拼接（原人生段的入行事实在段视图里，接管段的在终局账本里，occupationTrail 改吃段视图）。
- **子女槽**：段视图里出现过的子女事实都算玩家的子女线（原人生里生的孩子不会因为交换被写没）；若两段都有，按时间序各给一句（槽位文案在二期内容施工时按 COPY-AND-AI 补交换变体，不许结算硬编）。
- **父母槽**：段视图里 dad/mom 的 state 流转按时间序读，最后一次流转定收尾句；两段父母是两套轨迹（裁定三），槽文只讲玩家实际经历过的那几次（段视图天然只含玩家在场段）。
- **判词 verdict()**：只读终局身体的数值形状（判词讲的是这个人最后的样子），不改。
- **第八槽（另一条路）真账化**（新局）：读结算时不受控的那条 Track 的**全账本**（交接局即被换下那条的交接后全程，未交接局即 Track_B 全账本）：它的终局（死亡岁数或 80）+ **揭价对象从 meta.shownFacts 里选**（瞥视/悼念里真露过面的那件——地基 §3.6 成对回响：揭过的价必须对着露过的事说）；没露过面的事不许在结算凭空收费。对面早夭时，本槽用 6.3 的全生收尾骨架呈现，不因它活得短而缩水。文案形状：「另一条路（路线名）后来……（它的关键流转一句）。你在 X 岁看过的那件（素材复述），后来的价是……」——具体文案二期内容施工时写，蓝图只定取材与结构。legacy 局与「其他几条路」行维持模板版（那几条路本就没有真人生，模板是诚实的占位，与现行一致）。
- **分享卡**：吃 verdict + 九槽，自动继承段视图；路线行显示终局路线名，交换过的小字加一行「中途换过一条路」（share.js 小改）。

### 7.4 道路图交叉点与结算快进

- **快进**：`renderEnd` 首次结算时，若不受控 Track 存活且未 finalized：在 withLife 内把它无头步进到其死亡或 80（≤58 年，纯计算，毫秒级），置该 Track 条目的 `finalized=true` 并 save。第八槽与对照行读快进后的完整账本。受控 Track 先死的情况（5.1 冻结）也在此一并快进——没被选的那条路「也走完了它的一生」在结算页成为真话而不是模板话。
- **交叉点数据**：`meta.swap{age, from, to}` + 两条 Track 各自的关键节点（各自分岔落点读各自账本，段视图给玩家脊线）。`settlementMapHtml` 改造点：脊线 = 段视图的分岔序列（交接前原 Track 的、交接后接管 Track 的，chosenOfFork 改读段视图后天然成立）；在 swap.age 处画交叉——原路线线以虚线（既有未选支的灰虚线样式，不新造配色）从交叉点续到被换下 Track 的终局岁，接管路线以虚线从 22 岁（它出生处）引到交叉点、其后并入脊线；交叉点节点用既有实心点 + 标签「X 岁 · 换到了『路线名』那条路」。未交接局的图与现行逐像素一致（parity 的呈现侧：地图 HTML 在未交接局须与 v0.20.3 同种子同局逐字一致——进回归断言）。

## 八、分期与验收（问题 6）

沿用全项目质量门：每期收尾 = 数值门（quality-gate）+ 全记录审计（真局全记录、评审带引文）双轨，绿数不代替读记录。

### 8.1 一期完工定义（平行模拟 + 瞥视真账，无交换）

1. **出生与步进**：两条开局路径（序章汇入 / 卡牌开局）都生 Track_B；双 Track 并存于 v2 存档、控制权指针 = A；不受控 Track 逐年步进、会死、80 封顶；受控 Track 死亡后它冻结。sim 断言覆盖四年代 × 若干种子。
2. **parity 套件**（新增 `tools/parity-shadow.js` 并入 quality-gate）：取 v0.20.3 冻结种子集（regression/audit 两组现成种子），逐局比对主线 `ledger + log + 终局数值` 与 v0.20.3 基线转储——**逐字全等**才算过。基线转储在本轮动工第一步、改任何代码之前先生成并封存。
3. **双 Track 逐字节复现（政策纯函数的整局形状，硬卡点）**：sim determinism 模式扩双 Track——同种子双跑（第二次在新进程里跑），两条 Track 的账本 + 流水 + 终局状态逐字节全等；4.4 的 F 单元门并行过。任一字节差先查政策里的隐藏状态/随机源，再查步进。
4. **瞥视出处检查**（新增常设检查）：遍历 ≥4000 局的全部瞥视呈现记录——主/次素材逐字命中该局不受控 Track 的 log、现状事实表逐行对上它的 state/账本（含房贷/体检两类事实的来源登记核对）、悼念触发与 shownFacts 记账正确、事实表零预后措辞（禁用词表扫描）。命中率必须 100%（这是「读真账 + 两层标准」的可测形状）。
5. **影子分布 sanity + 死亡分布同口径对照**（16000 局主批附影子附表）：按年代 × 路线报不受控 Track 的终局岁数分布、成婚率、有子率、退休到达率，与主线同口径并排：终局岁数中位差 ≤2 岁、成婚/有子率差 ≤5 个百分点。其中**死亡年龄分布单列同口径对照**：按年代比三段占比（用死亡年代带同款段法），影子与主线逐段差 ≤3 个百分点——这是「无保底」的可测形状：影子不许系统性活得更久（保底嫌疑）也不许系统性更短（步进缺陷嫌疑）；超差只许查政策与步进，**不许调影子的死亡参数**。另表单列影子 30 岁前死亡率（悼念路径的负载预期）。影子零命中另表报告，不并入主线零命中口径（守历轮可比性）。
6. **主批护栏**：quality-gate 全套绿且主线终数与 v0.20.3 基线逐项同值（parity 的推论，出现差异按缺陷处理）。
7. **旧档**：oldsave 模式扩一条「v0.20.3 进行中存档（平铺旧形状）续玩至终局」用例：加载时包成 session（B = null）、legacy 瞥视与结算正常、无报错。
8. **全记录审计（一期版）**：16 局全新种子真机代码全记录（主线 + 影子双账本落盘），评审只读不受控 Track 侧查三件事——它像不像一个真人过完的一生（状态线自洽）、瞥视取材有没有编、悼念是否如实且有分量；缺陷带引文销账。

### 8.2 二期完工定义（交换全套）

1. **提问与交接**：脚本局断言——三个瞥视点（看了、对面活着、未换过、非悼念屏）各出一次提问，且机会说明行在位（DOM 断言）；拒绝后后续点仍问、说明行仍在；接受后验**交接纯度**：两条 Track 的 state 与 streams 在交接前后逐字段全等（只许两本账各多一条 swap 记账 + meta 变更 + 指针翻转），`IFY.S` 已改绑且重读一致；一生第二次交换永不出现（断言扫全批）。
2. **换后可玩完 + 接管容错**：交换局（30/40/50 各若干种子 × 四年代）全部能走到结算，被换下的 Track 由 Bot 继续步进并在结算快进收尾；4.5 的**极端状态接管测试集**全过（合成极端存档交 Bot 跑至终局：不抛错、不断链、必终止）；结算段视图断言——九槽事实逐槽对 controlLog 段账本（子女跨段、父母跨段、第八槽揭价对象 ∈ meta.shownFacts 三个专项断言）。
3. **带交换的确定性**：脚本化的「交换剧本局」（固定种子 + 固定交换点 + 人格后续选择）双跑，两本账 + 结算 HTML 全等。
4. **护栏（带交换口径）**：sim 人格加交换倾向（确定性规则：人格在其 40 岁瞥视时，若其性子权重与影子路线亲和更高则换——与政策同源逻辑，写进口径注），16000 局主批：死亡年代带（以终局身体计）、特殊总率 ≤13%、单体 ≤1%、结算对账冲突 0、零命中不净增（主线口径）全过；同时报 0% 交换口径（一期数）作地板对照。数字动了先定位是交换的真实后果还是缺陷，不许先调参。
5. **道路图**：交换局地图含交叉点且标签正确；未交换局地图与 v0.20.3 逐字一致（回归断言）。
6. **全记录审计（二期版）**：16 局双人生全记录（过半局带交换），全新评审五维盲读 + 交换专项三查——换后叙事连不连贯、代价揭得诚不诚实、被换下的人生有没有被贬低（红线 2 的读感面）。缺陷带引文。
7. **交付惯例**：版本号 v0.21.0（Y 位——新机制）、DEVLOG 一条、本蓝图附销账表、试玩单文件重打；推送等用户点头。

## 九、风险与代价（问题 7）

- **性能账**：玩家侧——每次 advance 多跑一年无头步进（一次 planYear + 若干 due 判定，纯计算无渲染），量级与 sim 单年步进相同，毫秒以下到个位数毫秒，手机上无感；结算快进 ≤58 年同理。二期交接本身是一次指针翻转，无持续成本。模拟侧——16000 局主批每局多活一条人生，边际成本近乎翻倍但不受控年免了呈现与审计仪表（sim 里不受控步进不做 era-scan 等逐文本仪表，只记账本）；预算：quality-gate 总墙钟 ≤ v0.20.3 的 1.8 倍，WP1 先测单局边际成本（关仪表、200 局预热后计时）再确认预算，超了先砍不受控侧仪表、不砍检查项。
- **存档与分享**：存档约 2 倍体积（实测记报告）；分享链接只带种子，零影响；每日局零影响。
- **结局率与零命中的连带**：一期按构造为零（parity 保证主线一切数字不动，影子是纯增量观测）。二期交换真实改变玩家轨迹——死亡带与结局率按 8.2.4 的双口径报告，这是机制的真实后果不是缺陷，但若某项破线，先查实现再议标定，不许顺手调参掩盖。
- **不受控 Track 的内容病灶**：两条 Track 共用同一事件池与全部 ctx 门——主线已知的五组系统项（职业漂移、路线泄漏、关系预设、退休阶段门、往事预设）在政策驱动的人生身上同样存在，且 Bot 走出的路径更多样，漂移类问题在它的账本里只会更显形，不会更少。二期交接后，玩家还会亲手过上一段 Bot 风格与玩家风格混杂的人生，状态组合的分布比纯 Bot 局更宽——4.5 的接管容错与极端状态测试集是这条风险的对冲。
- **与五组系统项的先后建议**：**v0.21 先行，五组随后，且用双人生审计记录当五组那轮的输入**。理由：① 交换是标题机制，有创始人定案的优先级，内容债不该排在它前面；② 一期的双账本审计恰好给五组提供双倍、且路径更杂的证据面，那轮的修复会同时治两条人生；③ 二期交换让玩家亲手接管影子人生，漂移的读感代价在二期后变高——所以五组那轮应紧跟 v0.21、不许再往后拖，但也不必卡在 v0.21 之前。次序定版：v0.21 一期 → v0.21 二期 → 五组系统项轮（双账本审计驱动）。
- **脆弱点登记**：① 瞥视 1 抽不变式（裁定二）——改瞥视呈现的人最容易顺手破它，靠 parity 套件 + 代码注释守；② 无头解决与呈现层的变更清单漂移——以后任何人改 render* 的状态变更，必须同步改无头解决器，WP2 把这条写进 shadow-life.js 文件头与 DEVLOG 本轮条目，审计清单加一项「变更清单对盘」；③ 政策即数值——政策权重直接决定不受控 Track 的人生分布，改政策等于改内容，升 policyV 并走与数值调校同样的实测报告口径；④ **政策纯度**——F 里任何一处顺手写的流抽取、模块级计数或备忘缓存都会静默打破逐字节复现，且只在 determinism 门上现形，靠 4.4 单元门 + 政策文件逐行评审守；⑤ **交接改绑**——交接后仍持有旧 `IFY.S` 引用的代码会把新人生写进旧 Track，靠 7.2 的改绑断言与「交接后重读」纪律守；⑥ **无保底的体感风险**——对面早夭的局，交换戏份天然变薄，可能有玩家觉得「这局没意思」；接受这个代价（6.3 的理由），靠悼念与结算的重量把短的局做成完整的局，不靠造假补。
